Remove Privileged Fields from User RPCs (web/src/db-fns/web/users.ts) The Issue: The CreateUserSchema (and by extension UpdateUserSchema) currently allows setting fields like role and billingStatus. Because updateUser does not validate if the caller is authorized to modify these fields, any user can escalate their privileges to admin or bypass billing gates by setting their status to active. The Fix: Remove role, billingStatus, stripeCustomerId, and stripePaymentMethodId from the Zod schemas used by the client RPCs. 2.  Preserve Billing Cycle Dates on Card Updates (web/src/db-fns/web/billing.ts) The Issue: When confirmSetupIntent is called (which happens when adding a new card), it unconditionally sets billingStartedAt to the current time and nextPaymentAt to one month in the future. If a user simply updates an expired card, their billing cycle resets, granting them a free month. The Fix: Update confirmSetupIntent to only set billingStartedAt and nextPaymentAt if they are currently null on the user or organization record. 3. Fix Retry Backoff Calculation (workers/app/domains/billing/application/workflows.py)The Issue: The Celery retry logic calculates retry_after based on period_end (which represents when the payment was due). If the worker has been offline and the due date is far in the past, the resulting retry_after timestamp will also be in the past. This will cause the worker to rapidly trigger retries without delay until the exponentially increasing backoff finally catches up to the current time. The Fix: Change the retry_after calculation to add the exponential backoff duration to the current UTC time instead of the period_end timestamp. 4. Prevent Duplicate Key Error for Zero-Dollar Charges (workers/app/domains/billing/application/workflows.py) The Issue: If a charge evaluates to $0 (e.g., if base pricing changes or a discount is applied), the code inserts the literal string 'no_charge_due' into the stripe_payment_intent_id column. Because this column has a UNIQUE constraint, the second $0 charge will crash the worker with a duplicate key violation. The Fix: Ensure uniqueness by changing the text and appending the attempt's UUID f"zero_due_{attempt['id']}"
